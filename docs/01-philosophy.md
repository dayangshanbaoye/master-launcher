# 01 · 设计哲学

## 两条原则

### 一、三种寻址，一个对象

> Search when you know. Browse when you don't. Gesture when you remember.
>
> 知道是什么，就搜，能动嘴就不动手。
> 只知道大概，就分类浏览。
> 已经形成习惯，就直接用手势。

传统启动器的 App Drawer + Folder + Home pages 是三套**互相独立**的组织方式，用户要同时维护三份心智地图：这个 app 在第几屏、在哪个文件夹、抽屉里排第几个。

这里的三个入口不是三种组织方式，是同一个对象的三种寻址方式。它们背后是同一张索引表、同一个排序器、同一组 `Target`。用户只需要维护一份心智：**东西就在那儿，我用最省力的方式够到它**。

三者的分工由用户对目标的确定程度决定，而不是由 app 的类型决定：

| 用户状态 | 入口 | 代价 |
|---|---|---|
| 知道叫什么 | 搜索（键盘或语音） | 输入 2–4 个字符 |
| 只知道是哪类 | 浏览 | 一次滑动 + 一次点击 |
| 每天都用 | 手势 | 一次滑动 |

### 二、复杂性归引擎

> Complexity belongs to the engine, not the surface.

复杂性必须留在：搜索索引、排名、拼音、Tags、App metadata、intent、gestures、cache。

不许暴露成：满屏按钮、多级菜单、设置项。

这条比视觉风格更重要。Warm Minimal 是结果，不是目标——如果引擎足够聪明，界面自然就没东西可放。

## 一个必须处理的副作用

"复杂性归引擎"的代价是**可发现性归零**。手势是隐藏的，用户不知道自己有什么；分类是引擎生成的，用户不知道为什么这么分。传统启动器满屏按钮很蠢，但它至少自证。

所以引擎除了"变聪明"，必须承担第二个职责：**主动提议**。

- 检测到某 app 连续 7 天进入 top-3，浮一张卡片："要不要把它绑到右下角滑？"
- 用户搜了三次没点任何结果，下次浮出："是不是在找 XX？"
- 手势速查表：主屏长按空白处，半透明浮现当前所有手势绑定，松手消失。不做常驻提示。

**手势不是用户配的，是引擎长出来的。** 这才让原则闭环。

## 判断依据

遇到拿不准的功能，按顺序问这三个问题：

1. 这个功能需要用户去某个界面配置它才能用吗？→ 是，则重新设计或砍掉。
2. 这个功能会往屏幕上加常驻元素吗？→ 是，则它必须替代掉一个已有元素，否则砍掉。
3. 这个功能能否表达成"某个 Query 返回某组 Target"？→ 不能，则它可能不属于启动器。

## 不做清单

以下方案已经过评估并明确排除，**不要重新提议**：

| 不做 | 原因 |
|---|---|
| 主题商店、图标包 | 把复杂性推回表层 |
| 多页 Home、小组件墙 | 同上，且与"三入口"冲突 |
| 手动文件夹 | 分类是引擎职责，不是用户劳动 |
| 集中式设置页 | 每一个设置项都是引擎的一次失败 |
| 意图短语直达会话（"给王晓东发消息"） | 微信等主流 app 没有公开的会话级 deep link，这不是权限问题而是对方没开门 |
| `NotificationListenerService` 读会话 | 高危权限 + 国产 ROM 后台清理不可靠，收益不抵成本 |
| `AccessibilityService` 模拟点击 | 灰产技术栈，会被下架，目标 app 改 UI 即失效 |
| 逆向私有 scheme | 无法维护 |
| Browse 里保留 app 图标 | 单色化后图标不再承载识别功能，只剩噪音；中文名 2–4 字读起来更快 |

意图短语的降级替代方案是索引 `LauncherApps.getShortcuts()`——app 自己发布的快捷方式（微信"扫一扫"、支付宝"付款码"），零额外权限，覆盖原设想 80% 的价值。这条**要做**，见需求文档 P1-2。
